# When Testimony Is Not Enough: Corrective-Evidence Delivery in Multi-Agent LLM Teams

This repository contains the code and analysis for *When Testimony Is Not
Enough: Corrective-Evidence Delivery in Multi-Agent LLM Teams*. Four LLM
agents solve a hidden-profile task in which one agent's private dossier
carries a false assessment and a second agent receives an
external record with the information necessary to disprove this false assessment. We vary how that record reaches the two
remaining agents across six delivery arms, and also whether each agent's assigned option is attributed to them. The primary model is GPT-5.4-mini, while Deepseek-V4-Pro is used as a cross-model check.

## Vocabulary

| Repository                             | Paper                                             |
| -------------------------------------- | ------------------------------------------------- |
| `corrector_agent` (schemas, records) | the verifier                                      |
| ordinary-neutral                       | ordinary agents                                   |
| scope ladder / correction scope        | delivery arms                                     |
| hidden corrected anchor                | the shared verifier response replayed across arms |

`tool_v2` is the internal name for everything reported in the paper,
and is the default when `--scope-ladder` is supplied.

All reported runs use `PROMPT_VERSION = v3.2`, recorded in each run's `run_manifest.json`.

## Repository map

- `data/scenarios_hidden_profile_candidates.json`: hidden-profile
  scenario packages and matched
  assumption variants.
- `src/assumption_propagation/orchestrator.py`: frozen-seed generation and
  synchronous propagation.
- `src/assumption_propagation/evidence.py`: deterministic canonical record and
  placebo payloads.
- `src/assumption_propagation/clients.py`: ordinary completion and forced-tool
  client flows.
- `src/assumption_propagation/topologies.py`: graph routing and role placement of agents.
- `src/assumption_propagation/metrics.py` and `analysis.py`: answer-level
  outcomes, within one conversation and across a run.

There are 33 scenarios with 66 variants (factual and
causal), plus 33 framing variants. These were excluded from the runs and are reserved for follow-up work.
The primary protocol uses factual and causal variants only;
`--scope-ladder.`Framing can be requested with
`--variants framing`.

## Start using

```bash
uv sync

# A no-cost run against the mock client, to check the install works.
uv run python scripts/run_pilot.py --client mock --scenario vendor_001

# The four primary arms, still on the mock client.
uv run python scripts/run_pilot.py --client mock --scenario vendor_001 \
  --variants factual --scope-ladder --scope-protocol tool_v2 --n-seeds 1 \
  --topologies looped_chain neutral_star fully_connected_mesh \
  --attribution both --skip-baselines --skip-independent --rounds 4 \
  --tag scope_smoke
```

Add `--scope-controls` for the two mechanism controls as well.

The confirmatory run is fixed by `scripts/run_tool_v2_azure_33.ps1`, which
refuses to start unless the corpus hash, deployment, and worktree all match.
The launchers are PowerShell and assume `.venv\Scripts\python.exe`; on Linux
or macOS run them under `pwsh`, or read the argument list out of the file and
call `scripts/run_pilot.py` directly.

The `condition` field in the run data uses these names:

| condition                            | paper                           |
| ------------------------------------ | ------------------------------- |
| `injection_tool_none`              | no correction                   |
| `injection_tool_testimony`         | testimony                       |
| `injection_tool_relay`             | exact relay                     |
| `injection_tool_direct`            | tool receipt                    |
| `injection_prompt_receipt_control` | prompt receipt                  |
| `injection_tool_placebo`           | tool placebo                    |
| `no_injection_baseline`            | honest baseline, no false claim |

## Reproducing the paper's tables and figures

The analysis artifacts behind every number in Section 4 are committed under
`outputs/raw/`. Three runs are used:

| Directory                                                        | Role                                        |
| ---------------------------------------------------------------- | ------------------------------------------- |
| `20260810_merged_confirmatory_scope33_gpt54mini_v32`           | primary,`azure:gpt-5.4-mini`              |
| `20260807_193819_azure_confirmatory_scope33_deepseekv4pro_v32` | cross-model check,`azure:deepseek-v4-pro` |
| `20260817_merge_scenarios_noauthority_gpt54mini`               | no-authority ablation                       |

```bash
uv sync
uv run python docs/figures/make_tables.py          # all eleven tab_*.tex
uv run python docs/figures/make_fig_results.py     # fig_results.{pdf,png}
uv run python docs/figures/make_fig_attribution.py # fig_attribution.{pdf,png}
uv run python docs/figures/make_fig_setup_rounds.py
```

`make_tables.py` reads `records.jsonl` from the model runs, which are both around 300 megabytes and cannot be included in an anonymized version of the repository. Request them if you need to rerun the table
generator. Everything else the generators read is committed.

With `records.jsonl` present, all eleven `.tex` tables regenerate identically to the committed copies. Table 1 is a design table with no numbers and is written by hand in the paper. Outputs are written next to the
generators in `docs/figures/`, overwriting them.

A further audit covers response dynamics which are not included in the statistics.

```bash
uv run python scripts/audit_disclosure_and_dynamics.py <run-dir> \
    --json <run-dir>/analysis/audit_disclosure_and_dynamics.json
```

It reports the anonymity-leak rate, deadlock rate by arm, accuracy by
round, seed recantation by arm, parse failures by cell, and the per-scenario
spread of the ordinary-agent outcome. Committed output for both runs is under
each run's `analysis/`.

This audit doesn't need `records.jsonl`. It falls back to
`analysis/disclosure_slice.jsonl.gz`, a verbatim projection of the transcripts down to the ten fields the disclosure analyses read, ~5 MB gz against ~300 MB. The numbers are identical either way, and where the transcripts are present the projection can be
re-derived and diffed:

```bash
uv run python scripts/make_disclosure_slice.py <run-dir> --verify
```

The finer-grained leak measurement runs off the same slice:

```bash
uv run python scripts/measure_anonymity_leakage.py <run-dir> \
    --json <run-dir>/analysis/anonymity_leakage.json
uv run python scripts/measure_anonymity_leakage.py --selftest   # 21 cases
```

A message counts as leaking if it makes a first-person claim of standing
("my dossier", "I was assigned") in the same clause as the speaker's own
option, with no other option in between. This is utilized to maximize the probability of detecting a leakage. On 200 flagged clauses labelled by
hand, 99.0% were genuine (Wilson 95% CI 96.4-99.7).

Only the `anonymous` column is a leak rate. Under `assigned` the header
already names the assignment, so disclosure there is 100% by default and
the number shown counts only what the message body indicates.

`analysis/statistics_secondary.json` is regenerated rather than original; it
is produced by

```bash
uv run python scripts/analyze_statistics.py <run-dir> \
    --by-attribution --by-topology --json <run-dir>/analysis/statistics_secondary.json
```

Each run's `run_manifest.json` records the sha256 of `results.jsonl` under
`status.observed_files`, and `.gitattributes` pins `outputs/raw/**` to `-text`.

## Naming

Schemas call the designated verifier `corrector_agent`. Analysis reports it as
the verifier and keeps it out of ordinary-agent outcomes, so the field name and
the paper's term refer to the same agent.
